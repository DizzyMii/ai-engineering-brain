## 1. Confident hallucination despite correct retrieval
**Symptom:** the [[Concept - Rerankers|reranker]] and retriever both worked. The gold chunk sits at position 1 in the context, and the model still answers wrong, sometimes stating the *opposite* of the retrieved text, with no hedging. **Cause:** the generator's parametric prior overrides the provided context. RAG puts retrieved text in front of the model, but nothing forces the model to *use* it. A strong pretrained belief (or a common wrong pattern in training data) can outvote a single retrieved passage, especially on numbers, dates, and anything the model "confidently knows" a different answer to. **Fix:** a cite-or-abstain prompt ("answer only using the provided context; if the context doesn't contain the answer, say so"), structured output that forces a citation per claim, and in the worst cases a second grounding pass that checks each generated sentence against the retrieved spans. **Detection:** a faithfulness/groundedness metric (does every claim in the answer trace to a retrieved sentence?) run continuously via [[Concept - RAG Evaluation]], not spot-checked once at launch. This is the most expensive gotcha on the list, because the answers *look* authoritative and pass casual review.

## 2. Retrieved-but-ignored: right context, wrong answer
**Symptom:** recall@k on the golden set is fine and the correct chunk is in the top-k, but end-to-end answer accuracy lags the retrieval numbers. **Cause:** position bias inside the context window. In the lost-in-the-middle effect, information buried mid-context gets less effective attention than information at the start or end, whatever its relevance rank. Stuff 10 chunks in retrieval order (not relevance order) and the best evidence often isn't where the model reads most carefully. **Fix:** rerank before generation, put the highest-scored chunk first (or last, per your model's measured position curve), and cut k instead of padding the prompt with marginal chunks. **Detection:** a context-utilization metric. Does the answer track *which* chunk ranked highest, or ignore chunk order? Shuffle chunk order on the same query and watch whether accuracy moves.

## 3. The demo-to-prod eval gap
**Symptom:** the system looked great in a walkthrough with five hand-picked queries, then degrades unpredictably under real traffic, and nobody can say *which* change (new chunker, swapped embedder, prompt tweak) helped or hurt. **Cause:** chunk size, embedding model, k, rerank threshold and prompt wording were all tuned on vibes with no fixed measurement, so a regression can't be traced to a cause. **Fix:** build a golden set of 50-200 real query→relevant-chunk→answer triples *before* tuning anything, and re-run it after every pipeline change, per [[Concept - RAG Evaluation]]. **Detection:** if you can't answer "what's our current recall@10 and faithfulness score" with a number from the last 24 hours, you have this problem now. It's the meta-gotcha that lets every other one here go unnoticed.

## 4. Embedding-prefix omission silently halves recall
**Symptom:** recall craters after a migration or fresh deployment. No errors, no exceptions, and an embedding model that "should" work. **Cause:** asymmetric embedding models like E5 and BGE expect an instruction prefix (`query: ` vs `passage: `) on the input. Omit it and the model still returns a normally shaped vector, so nothing crashes. Queries and passages just land in subtly wrong regions of the space, and ranking degrades with no signal. Because it fails silently, it's one of the most common production bugs. **Fix:** check the prefix convention for the model you deploy (it varies by family) and bake it into the embedding client so a new call site can't forget it. **Detection:** A/B recall on the golden set with and without the prefix. A 10-20+ point swing in recall@10 confirms the bug.

## 5. Chunk-boundary amputation
**Symptom:** a chunk retrieves correctly but is useless: a table row with no header, a function split from its signature, a sentence starting mid-clause. **Cause:** naive fixed-size or recursive-character [[Concept - Chunking Strategies|chunking]] splits on token or character counts and ignores document structure, so tables, code blocks and long logical units get cut wherever the size limit falls. **Fix:** structural chunking (split on Markdown/HTML headers or code AST boundaries) for structured content, plus small-to-big / parent-document retrieval, so the *embedded* unit is small and precise and the *returned* unit is the full parent with its context. **Detection:** spot-check a sample of retrieved chunks for self-containedness. Could a human answer the query from the chunk alone, without the source document?

## 6. Distribution shift on domain jargon
**Symptom:** retrieval works on general queries and fails on domain-specific ones: legal citations, medical terms, internal product codenames, code identifiers. **Cause:** general-purpose [[Concept - Embedding Models|embedding models]] are trained on broad web/QA data and haven't seen your vocabulary densely enough to place it well. The failure is invisible because the model still returns *a* ranked list, just the wrong one. **Fix:** hybrid search as a cheap first defense (dense catches paraphrase, [[Concept - BM25 and Lexical Retrieval|BM25]] catches the exact rare terms dense embedders blur together), then in-domain fine-tuning or a domain-specific embedder (code, legal, medical variants) if the gap persists. **Detection:** segment recall@k by query type (general vs jargon-heavy) on the golden set. The aggregate number hides this, since domain queries are usually a minority of the eval set and the majority of the pain.

## 7. Near-duplicate flooding and over-retrieval noise
**Symptom:** the top-k is dominated by five near-identical restatements of one fact from different document versions, crowding out distinct evidence. Or the reverse: a large k pulls in tangential chunks that measurably *lower* answer accuracy. **Cause:** dense retrieval ranks by similarity, and near-duplicates are by definition maximally similar, so without dedup they take over the ranking. Separately, context isn't free. Each extra chunk is another chance to inject a distractor that competes with the right answer for attention, and it compounds with the lost-in-the-middle effect from gotcha #2. **Fix:** deduplicate at index time or apply MMR (maximal marginal relevance) at retrieval time to trade relevance against diversity, and tune k on the golden set instead of assuming bigger is safer. **Detection:** plot accuracy against k on the golden set. If it peaks and then declines, you're past the point where more retrieval helps.

## 8. Stale index and delete tombstones
**Symptom:** answers cite outdated facts (an old price, a superseded policy) even though the source was updated, or query latency creeps up over weeks with no code change. **Cause:** updating a source document doesn't recompute and re-index its embedding. Many pipelines run ingestion as a one-time batch job, so the index drifts from ground truth without anyone noticing. Deleted documents also leave tombstones in ANN indexes like [[Concept - HNSW|HNSW]], which pile up and degrade recall and latency (index-level mechanics in [[Gotchas - Vector Index Tuning]]). **Fix:** treat the index as a versioned, incrementally synced artifact tied to document change events, and schedule periodic full rebuilds to clear tombstones. **Detection:** monitor index staleness (time since last sync per document) and deleted-ratio alongside query latency and error rate, via [[Concept - LLM Observability and Tracing]].
