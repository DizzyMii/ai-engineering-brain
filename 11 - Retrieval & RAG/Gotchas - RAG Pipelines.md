## 1. Confident hallucination despite correct retrieval
**Symptom:** The [[Concept - Rerankers|reranker]] and retriever both did their job — the gold chunk sits at position 1 in the context — and the model still answers wrong, sometimes stating the *opposite* of what the retrieved text says, with no hedging. **Cause:** the generator's parametric prior overrides the provided context. RAG grounds the model in retrieved text, but nothing forces the model to actually *use* it; a strong pretrained belief (or a common but wrong pattern in training data) can outvote a single retrieved passage, especially on numeric facts, dates, and anything the model "confidently knows" a different answer to. **Fix:** an explicit cite-or-abstain prompt ("answer only using the provided context; if the context doesn't contain the answer, say so"), structured output that forces a citation per claim, and in the worst cases a second grounding pass that checks each generated sentence against the retrieved spans. **Detection:** a faithfulness/groundedness metric — does every claim in the answer trace to a retrieved sentence — run continuously via [[Concept - RAG Evaluation]], not just spot-checked at launch; this is the single most expensive gotcha on the list because it produces answers that *look* authoritative and pass casual review.

## 2. Retrieved-but-ignored: right context, wrong answer
**Symptom:** recall@k on the golden set is fine, the correct chunk is in the top-k, but end-to-end answer accuracy still lags the retrieval numbers. **Cause:** position bias inside the context window — the classic lost-in-the-middle effect, where information buried in the middle of a long context gets less effective attention than information at the start or end, regardless of relevance ranking. Stuffing 10 chunks in retrieval order (not relevance order) means the best evidence is often not where the model reads most carefully. **Fix:** rerank before generation and place the highest-scored chunk first (or last, per your model's empirically measured position curve), and reduce k rather than padding the prompt with marginal chunks. **Detection:** a context-utilization metric — does the answer correlate with *which* chunk was ranked highest, or is it agnostic to chunk order — swept across position by deliberately shuffling chunk order on the same query and watching accuracy move.

## 3. The demo-to-prod eval gap
**Symptom:** the system looked great in a walkthrough with five hand-picked queries and then degrades unpredictably once real traffic hits it, and nobody can say *which* change (a new chunker, a swapped embedder, a prompt tweak) helped or hurt. **Cause:** every RAG decision — chunk size, embedding model, k, rerank threshold, prompt wording — was tuned against vibes instead of a fixed measurement, so there is no way to attribute a regression to a cause. **Fix:** build a golden set of 50-200 real query→relevant-chunk→answer triples *before* tuning anything, and re-run it after every pipeline change, per [[Concept - RAG Evaluation]]. **Detection:** if you cannot answer "what's our current recall@10 and faithfulness score" with a number from the last 24 hours, you're in this failure mode right now — it is the meta-gotcha that lets every other gotcha on this list go unnoticed.

## 4. Embedding-prefix omission silently halves recall
**Symptom:** recall craters after a migration or a fresh deployment, with no errors, no exceptions, and an embedding model that "should" be working. **Cause:** asymmetric embedding models like E5 and BGE require an instruction prefix (`query: ` vs `passage: `) on the input text; the model still returns a normally-shaped vector if you omit it, so nothing crashes — it just embeds queries and passages into subtly wrong regions of the space, degrading ranking quality without any signal that something is broken. This is one of the most common production bugs precisely because it fails silently. **Fix:** verify the prefix convention for whichever model you deploy — it varies by model family — and bake it into the embedding client so it can't be forgotten at a new call site. **Detection:** an A/B recall test on the golden set with and without the prefix; a 10-20+ point swing in recall@10 confirms the bug.

## 5. Chunk-boundary amputation
**Symptom:** a chunk retrieves correctly but is useless — a table row with no header, a code function split from its signature, a sentence that starts mid-clause. **Cause:** naive fixed-size or recursive-character [[Concept - Chunking Strategies|chunking]] splits on token or character counts with no awareness of document structure, so tables, code blocks, and long logical units get sliced arbitrarily wherever the size limit lands. **Fix:** structural chunking (split on Markdown/HTML headers or code AST boundaries) for structured content, and small-to-big / parent-document retrieval so the *embedded* unit is small and precise while the *returned* unit is the full parent with context intact. **Detection:** spot-check a sample of retrieved chunks for self-containedness — can a human answer the query from the chunk alone without seeing the source document.

## 6. Distribution shift on domain jargon
**Symptom:** retrieval works fine on general queries and quietly fails on domain-specific ones — legal citations, medical terminology, internal product codenames, code identifiers. **Cause:** general-purpose [[Concept - Embedding Models|embedding models]] are trained on broad web/QA data and have never seen your domain's vocabulary densely enough to place it correctly in embedding space; the failure is invisible because the model still returns *a* ranked list, just not the right one. **Fix:** hybrid search (dense catches paraphrase, [[Concept - BM25 and Lexical Retrieval|BM25]] catches exact rare terms lexical embedders blur together) as a cheap first line of defense, and in-domain fine-tuning or a domain-specific embedder (code, legal, medical variants) when the gap persists. **Detection:** segment recall@k by query type (general vs domain-jargon-heavy) on the golden set — an aggregate recall number hides this because domain queries are usually the minority of the eval set but the majority of the pain.

## 7. Near-duplicate flooding and over-retrieval noise
**Symptom:** the top-k list is dominated by five near-identical restatements of the same fact from different document versions, crowding out genuinely distinct evidence — or, symmetrically, a large k pulls in tangential chunks that measurably *lower* answer accuracy rather than helping. **Cause:** dense retrieval ranks by similarity, and near-duplicate content is by definition maximally similar, so without deduplication it dominates the ranking; separately, more context is not free — every additional chunk is a chance to inject a distractor that competes with the correct answer for the model's attention, especially interacting with the lost-in-the-middle effect from gotcha #2. **Fix:** deduplicate at index time or apply MMR (maximal marginal relevance) at retrieval time to explicitly trade off relevance against diversity, and tune k against the golden set rather than assuming bigger is safer. **Detection:** measure accuracy as a function of k on the golden set — if accuracy peaks and then declines as k grows, you're past the point where more retrieval helps.

## 8. Stale index and delete tombstones
**Symptom:** answers reference outdated facts (an old price, a superseded policy) even though the source document was updated, or query latency creeps up over weeks with no code change. **Cause:** updating a source document doesn't automatically recompute and re-index its embedding — many pipelines treat ingestion as a one-time batch job rather than a live sync — so the index silently drifts from ground truth; separately, deleted documents leave tombstones in ANN indexes like [[Concept - HNSW|HNSW]] that accumulate and degrade both recall and latency over time (see [[Gotchas - Vector Index Tuning]] for the index-level mechanics). **Fix:** treat the index as a versioned, incrementally-synced artifact tied to document change events, not a one-off load, and schedule periodic full rebuilds to clear tombstone accumulation. **Detection:** track index staleness (time since last sync per document) and deleted-ratio as first-class monitoring metrics via [[Concept - LLM Observability and Tracing]], not just query latency and error rate.
