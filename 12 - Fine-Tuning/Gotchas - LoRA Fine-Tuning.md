## 1. Target modules default to q,v only: quality caps out well below full FT
**Symptom:** the LoRA fine-tune trains cleanly and loss drops, but held-out task quality plateaus noticeably below full fine-tuning even at generous rank. **Cause:** the original [[Deep Dive - LoRA]] paper (Hu et al. 2021) targeted only the attention query and value projections, and many config templates still default to `target_modules=["q_proj","v_proj"]`. The adapter then has no path into the MLP (gate/up/down projections), where most of a transformer's parameter and FLOP budget, and most of its adaptation capacity, lives. **Fix:** target all linear layers (`target_modules="all-linear"` in HF `peft`, or list q,k,v,o,gate,up,down explicitly). Coverage matters more than rank for closing the gap to full FT. **Detection:** compare a q,v-only run with an all-linear run at the same rank on a held-out eval. If all-linear wins by more than noise, you were leaving quality behind.

## 2. Changing rank without adjusting alpha silently rescales the effective learning rate
**Symptom:** you raise rank from 16 to 64 for capacity and the loss curve barely moves, or diverges. **Cause:** the LoRA update is `dW = (alpha/r) · B @ A`. Alpha and r are separate knobs, but their ratio sets the update's effective magnitude. Copy an `alpha=32` config from an `r=16` run into an `r=64` run and the multiplier silently drops from 2.0 to 0.5, a 4x smaller effective step, with no config error to warn you. Full mechanism in [[Concept - rsLoRA and the Rank-Alpha Scaling Trap]]. **Fix:** keep `alpha/r` roughly constant when changing rank (the `alpha=2r` convention), or switch to rank-stabilized scaling (`use_rslora=True`), which scales by `alpha/sqrt(r)` and keeps the update magnitude roughly rank-invariant. **Detection:** if raising rank changes nothing or stalls the loss curve, check whether alpha moved with it before concluding "rank doesn't help here."

## 3. Gradient checkpointing on a frozen or quantized base needs explicit input-grad wiring
**Symptom:** loss doesn't move at all from step 0, despite a reasonable LR and correctly formatted data. **Cause:** gradient checkpointing recomputes activations during the backward pass, which needs the input to the first trainable op to have `requires_grad=True`. With a frozen base (every base param has `requires_grad=False`) nothing sets that flag, so autograd has no path to build a graph and the backward pass does effectively nothing. **Fix:** call `model.enable_input_require_grads()`, or for a quantized base use `prepare_model_for_kbit_training(model)`, which wires this up and also normalizes layer-norm dtype. **Detection:** the signature is a truly flat loss (not slowly decreasing) from the first logged step, on a model that trains fine with checkpointing off. Checkpointing plus a frozen base is the near-universal cause.

## 4. Merging a QLoRA adapter into a 4-bit base loses accuracy compared with running the adapter live
**Symptom:** the merged, standalone model scores measurably worse than the same adapter running on top of the 4-bit base at inference. **Cause:** merging computes `W_merged = W + (alpha/r) · B A`. If `W` is still stored in 4-bit NF4, the merge either runs in the wrong precision or bakes in the base's quantization error a second time. [[Concept - QLoRA]] explains why: the base's quantization error is fixed at training time, and the adapter learns to compensate for that fixed error, not for a re-quantized version of it. **Fix:** dequantize the base to fp16/bf16 first, then merge in that precision: `merge_and_unload()` after loading in full precision, never on a 4-bit-loaded model. **Detection:** run the same eval on (a) adapter-on-4bit-base and (b) the merged-then-requantized model. A gap means the merge step is the problem, not the adapter.

## 5. Added or resized token embeddings aren't trained by a standard LoRA config
**Symptom:** after adding new special tokens or resizing the vocabulary (e.g. a tool-call token), the model emits garbage or near-random output whenever that token appears. **Cause:** a standard LoRA config only attaches adapters to the linear layers in `target_modules`. The embedding table and LM head stay frozen at their pretrained values, and the "pretrained" value for a token you just added is untrained random init. **Fix:** add `embed_tokens` and `lm_head` to `modules_to_save` so they're fully fine-tuned (not low-rank adapted) alongside the LoRA layers. This ties directly to how the base model's [[Concept - Byte-Pair Encoding]] vocabulary was built, since you're extending it after the fact. **Detection:** if quality on the new-token path is catastrophically worse than on existing-vocabulary paths while everything else looks fine, check whether the embedding/head are in `modules_to_save`.

## 6. Saved adapter reloaded against a different base revision degrades silently
**Symptom:** an adapter that did well in training and eval performs noticeably worse, with no errors, after a redeploy weeks later. **Cause:** `save_pretrained` on a LoRA adapter saves only `A` and `B`, the low-rank delta, not the base weights. If the base is re-pulled from a registry and the revision has moved (a maintainer's re-upload, a quantization re-pack, even a routine retag), the delta was computed against a `W` that's no longer the `W` it's being added to. **Fix:** pin and record the exact base-model revision or commit hash with every saved adapter, and verify it at load time. **Detection:** a quality drop with an unchanged adapter file and unchanged eval set almost always means the base checkpoint changed underneath it. Diff the base model's hash between the working and broken runs.

## 7. Precision and composition edge cases: fp32 norms, double-merging, and QLoRA under ZeRO-3
**Symptom:** intermittent NaN losses under mixed precision; a LoRA trained on top of an already-merged LoRA model underperforms; QLoRA training under DeepSpeed [[Concept - Data Parallelism and ZeRO]] stage 3 throws sharding errors or silently corrupts the 4-bit weights. **Cause:** normalization layers and softmax are numerically fragile and generally need to stay fp32 even when the rest of the model runs in bf16 ([[Concept - Mixed Precision Training]] and [[Concept - Floating Point for Deep Learning]] explain why). Stacking a second LoRA on an already-merged model folds the first merge's low-rank approximation error into the second adapter's target weights. And ZeRO-3 shards parameters across ranks by default, which doesn't compose cleanly with bitsandbytes' 4-bit parameter storage without careful framework integration. **Fix:** make sure norm layers are excluded from autocast and kept fp32. Train a fresh adapter against the true original base instead of chaining merge-then-re-LoRA where you can. Check your framework's (e.g. axolotl, Unsloth; see [[Breakdown - Unsloth]]) tested ZeRO-3 + QLoRA compatibility before assuming it works out of the box. **Detection:** NaN losses that appear only under mixed precision (not fp32) point to a norm-layer dtype bug. Unexplained quality loss after a second round of LoRA training points to compounded merge error.
