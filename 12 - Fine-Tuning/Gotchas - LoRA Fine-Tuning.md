## 1. Target modules default to q,v only — quality caps out well below full FT
**Symptom:** the LoRA fine-tune trains cleanly, loss drops, but held-out task quality plateaus noticeably below full fine-tuning even at generous rank. **Cause:** the original [[Deep Dive - LoRA]] paper (Hu et al. 2021) targeted only the attention query and value projections, and many config templates still default to `target_modules=["q_proj","v_proj"]`. The adapter then has no path into the MLP (gate/up/down projections), which is where most of a transformer's parameter and FLOP budget — and most of its adaptation capacity — actually lives. **Fix:** target all linear layers (`target_modules="all-linear"` in HF `peft`, or explicitly list q,k,v,o,gate,up,down) — coverage matters more than rank for closing the gap to full FT. **Detection:** compare a q,v-only run against an all-linear run at the same rank on a held-out eval; if all-linear wins by more than noise, you were leaving quality on the table.

## 2. Changing rank without adjusting alpha silently rescales the effective learning rate
**Symptom:** you raise rank from 16 to 64 expecting more capacity and the loss curve barely moves, or diverges outright. **Cause:** the LoRA update is `dW = (alpha/r) · B @ A`; alpha and r are independent knobs but their ratio sets the update's effective magnitude. Copying an `alpha=32` config from an `r=16` run into an `r=64` run silently changes the multiplier from 2.0 to 0.5 — a 4x smaller effective step, with no config error to warn you. See [[Concept - rsLoRA and the Rank-Alpha Scaling Trap]] for the full mechanism. **Fix:** either keep `alpha/r` roughly constant when changing rank (the `alpha=2r` convention), or switch to rank-stabilized scaling (`use_rslora=True`), which scales by `alpha/sqrt(r)` and keeps the update magnitude roughly rank-invariant. **Detection:** if raising rank produces no quality change or a stalled loss curve, check whether alpha moved with it before concluding "rank doesn't help here."

## 3. Gradient checkpointing on a frozen or quantized base needs explicit input-grad wiring
**Symptom:** loss is exactly flat from step 0 — not slowly converging, genuinely unmoving — despite a reasonable LR and correctly formatted data. **Cause:** gradient checkpointing recomputes activations during the backward pass, which requires the input to the first trainable op to have `requires_grad=True`; with a frozen base (every base param has `requires_grad=False`) that flag is never set automatically, so autograd has no path to build a graph and the backward pass is effectively a no-op. **Fix:** call `model.enable_input_require_grads()`, or for a quantized base use `prepare_model_for_kbit_training(model)`, which wires this up along with normalizing layer-norm dtype. **Detection:** a genuinely flat loss (not slowly decreasing) from the very first logged step, on a model that trains fine with checkpointing disabled, is the signature — checkpointing plus a frozen base is the near-universal cause.

## 4. Merging a QLoRA adapter into a 4-bit base loses accuracy relative to running the adapter live
**Symptom:** the merged, standalone fine-tuned model scores measurably worse than running the same adapter on top of the 4-bit base at inference time. **Cause:** merging computes `W_merged = W + (alpha/r) · B A` — but if `W` is still stored in 4-bit NF4, the merge either happens in the wrong precision or re-bakes the base's quantization error a second time; see [[Concept - QLoRA]] for why the base's quantization error is fixed at training time and the adapter learns to compensate for exactly that fixed error, not for a re-quantized version of it. **Fix:** dequantize the base to fp16/bf16 first, then merge in that precision — `merge_and_unload()` after loading in full precision, never on a 4-bit-loaded model. **Detection:** run the same eval on (a) adapter-on-4bit-base and (b) merged-then-requantized model; a gap here means the merge step, not the adapter, is the problem.

## 5. Added or resized token embeddings are not trained by a standard LoRA config
**Symptom:** after adding new special tokens or resizing the vocabulary (e.g. a tool-call token), the fine-tuned model emits garbage or near-random output whenever that token appears. **Cause:** a standard LoRA config only attaches adapters to the linear layers listed in `target_modules`; the embedding table and LM head stay frozen at their pretrained values, and the pretrained value for a token you just added is literally untrained random init. **Fix:** add `embed_tokens` and `lm_head` to `modules_to_save` so they're fully fine-tuned (not low-rank adapted) alongside the LoRA layers — this interacts directly with how the base model's [[Concept - Byte-Pair Encoding]] vocabulary was built, since you're extending that vocabulary after the fact. **Detection:** if quality on the new-token path is catastrophically worse than on existing-vocabulary paths while everything else looks fine, check whether the embedding/head are in `modules_to_save`.

## 6. Saved adapter reloaded against a different base checkpoint revision degrades silently
**Symptom:** an adapter that worked well in training and eval performs noticeably worse, with no errors, after being redeployed weeks later. **Cause:** `save_pretrained` on a LoRA adapter saves only `A` and `B` — the low-rank delta — not the base weights; if the base model is re-pulled from a registry and the revision has moved (a maintainer's re-upload, a quantization re-pack, even a routine retag), the adapter's delta was computed against a `W` that's no longer the `W` it's now being added to. **Fix:** pin and record the exact base-model revision or commit hash alongside every saved adapter, and verify it at load time. **Detection:** a quality drop with an unchanged adapter file and an unchanged eval set almost always traces to the base checkpoint changing underneath it — diff the base model's hash between the working and broken runs.

## 7. Precision and composition edge cases: fp32 norms, double-merging, and QLoRA under ZeRO-3
**Symptom:** intermittent NaN losses under mixed precision; a LoRA trained on top of an already-merged LoRA model performs worse than expected; QLoRA training under DeepSpeed [[Concept - Data Parallelism and ZeRO]] stage 3 throws sharding errors or silently corrupts the 4-bit weights. **Cause:** normalization layers and softmax are numerically fragile and generally need to stay fp32 even when the rest of the model runs in bf16 (see [[Concept - Mixed Precision Training]] and [[Concept - Floating Point for Deep Learning]] for why); stacking a second LoRA on top of an already-merged model compounds the first merge's low-rank approximation error into the second adapter's target weights; and ZeRO-3 shards parameters across ranks by default, which doesn't compose cleanly with bitsandbytes' 4-bit parameter storage without careful framework integration. **Fix:** confirm norm layers are excluded from autocast and kept fp32; avoid chaining merge-then-re-LoRA when you can instead train a fresh adapter against the true original base; check your training framework's (e.g. axolotl, Unsloth — see [[Breakdown - Unsloth]]) tested ZeRO-3 + QLoRA compatibility before assuming it works out of the box. **Detection:** NaN losses appearing only under mixed precision (not fp32) point to a norm-layer dtype bug; unexplained quality loss after a second round of LoRA training points to compounded merge error.
