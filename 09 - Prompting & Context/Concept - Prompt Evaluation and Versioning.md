# Concept - Prompt Evaluation and Versioning

A prompt is a piece of production logic with a decision boundary as complex as any model it steers, yet it is routinely edited by pasting a new string into a chat UI, with no test suite, no version pin, and no regression gate. Treating prompts as versioned, evaluated artifacts — the same discipline applied to application code — is what separates a system that survives a provider's silent model update from one that quietly degrades in production for weeks before anyone notices.

## The mechanism
Two properties make prompts fragile in a way ordinary code isn't. First, a prompt's behavior is only well-defined for one model snapshot: the exact weights it was tuned against. Swap the underlying model — even a "minor" version bump from the provider — and the same string can produce systematically different outputs, because nothing about the prompt itself changed but the function mapping it to a distribution over completions did. This means a prompt and a model version are one inseparable unit, and versioning one without the other is meaningless. Second, prompt behavior is not unit-testable in the traditional sense — there's no single correct output string to assert equality against — so "testing" a prompt means running it over a curated, labeled holdout set of representative inputs and scoring the *distribution* of outputs against expected properties: exact-match for narrow tasks, a rubric for open-ended ones, or [[Concept - LLM-as-Judge]] when a rubric can't be reduced to a simple string check. Because the judge itself is a noisy, imperfectly calibrated model with known position, verbosity, and self-preference biases, scores from an eval run are estimates, not ground truth, and should carry confidence intervals rather than being read as a single point number (see [[Concept - Statistical Rigor in Model Evaluation]] for the mechanics of computing them correctly on typically small holdout sets).

The practical unit this discipline builds is: `(prompt_version, model_version) -> eval_score_with_CI` — a lookup you can regenerate on demand and diff against the previous one whenever either input changes.

## In practice
Prompts belong in git or a dedicated prompt registry, with the model version they were validated against pinned alongside them and a changelog entry describing the *behavioral* intent of each edit (not just the diff, but what the edit was supposed to fix or change). Every prompt edit and every model upgrade should re-run the full eval set before rollout — these are the two events that most commonly break a previously-working prompt, and they need the same regression gate a code change to a critical function would get. "Prompt drift" — a provider silently updates the model behind an API endpoint or deprecates a snapshot, and your prompt's behavior shifts with zero code change on your end — is a real, recurring production incident class, distinct from and often harder to catch than a bug you introduced yourself, because nothing in your diff explains the regression.

For changes too risky to ship blind, route a fraction of live traffic to the new prompt (A/B or canary) and compare online metrics against the incumbent, guarding against small-sample false positives the same way any other online experiment would (again, [[Concept - Statistical Rigor in Model Evaluation]]). A format-sensitivity guardrail is essential here: because trivial formatting choices can swing accuracy by tens of points (see [[Concept - Prompt Formatting and Sensitivity]]), freeze one format per prompt version and don't let ad hoc "quick fixes" drift it — a format change is a new version, evaluated like any other. Keep eval-set inputs strictly out of any few-shot exemplar block used in the prompt itself, or you contaminate your own measurement (see [[Concept - Benchmark Contamination]] for the general failure mode this mirrors). Production tooling for this discipline includes promptfoo, LangSmith, and Braintrust for eval-set management and regression testing, and OpenAI Evals as a framework-level primitive; whichever is used, log the prompt version, the model version, and a hash of both on every production call so a metric regression can be correlated back to its cause after the fact (see [[Concept - LLM Observability and Tracing]] for the infrastructure this logging plugs into).

## Failure modes
Without a holdout set, a prompt gets hand-tuned against whatever handful of examples the author happened to try — classic overfitting to a demo, invisible until real traffic surfaces the cases that weren't tried. An unpinned model version turns every provider-side update into a silent regression risk: the prompt that scored well last month may score differently today with no local change to point to. And because a judged metric (LLM-as-judge or even a human rubric) is itself optimizable, iterating a prompt purely to raise the judge's score without periodically sanity-checking against a different judge or a human spot-check invites Goodharting the eval rather than actually improving the underlying task performance — the same trap that occurs in general model evaluation, imported wholesale into prompt-level iteration.

## The non-obvious
Most teams' first "prompt versioning" system is a comment in the code (`// v3, works better than v2`) — this fails specifically at the moment it matters most: correlating a live incident back to its cause. The fix that actually holds up in production isn't a nicer changelog, it's making `(prompt_version, model_version)` a first-class field on every logged request, computed as a hash and stamped before the call goes out. When an eval score or a user-facing metric regresses, the very first diagnostic step is "did the hash distribution change" — and if that answer isn't queryable from your logs, you're debugging blind no matter how disciplined your git history looks. Teams that skip this step consistently rediscover it the hard way, after a provider-side model swap they didn't initiate causes a metric drop they can't immediately attribute to anything.
